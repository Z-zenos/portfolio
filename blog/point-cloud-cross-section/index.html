Slicing Millions of Points in the Browser Without Jank

2026-10-16 · 14 min read

  • webgl
  • performance
  • point cloud

Pick A, pick B, and look sideways through the point cloud. I wanted a profile that made changes in elevation easy to inspect while leaving the 3D view responsive. The geometry fits into two dot products. The harder part was getting every matching point exactly once, keeping small distances accurate, and stopping old work when the user changed the question.

Why I wrote an extractor

The viewer already had a profile tool, so I first tried wrapping it in a clearer UI. I compared its output on a COPC point cloud with a small prototype that visited each octree node once.

The built-in request returned the same points repeatedly. Loading a node triggered another walk through descendants already queued, and a hierarchy-step fallback made that happen at every level in this code path. Some colours were wrong too: the decoder's packed colour stride disagreed with the stride inferred from the allocated buffer. Buffer capacity is not a reliable description of its layout.

Other datasets reproduced the duplication. That pointed to the library integration I was using, rather than one malformed file; it says nothing about every version of the library. Its coordinate output and update-loop scheduling also limited my control. I wrote an extractor with explicit traversal, precision, and cancellation rules.

Station and offset

Picture a strip of tape of width W stuck on the floor between two stakes A and B. For any point P, I want two numbers: how far along the tape it is from A (the station, the profile's horizontal axis), and how far left or right of the centre line it sits (the offset).

I work in a projected Cartesian frame with x and y in metres, not longitude and latitude. Points and node boxes must use that same frame. Both numbers come from the dot product. Let u be the unit vector from A to B: subtract A from B, divide by the length L. The left-hand normal is u rotated 90° counter-clockwise: n = (−u.y, u.x). Then, with AP = P − A:

  • s = AP · u is the shadow of AP on the A→B line, signed: negative means behind A.
  • t = AP · n is the sideways distance, positive on the left.

Since u and n are perpendicular unit vectors, this is just "move the origin to A, then rotate", and distances are preserved. A synthetic example: A = (0, 0), B = (30, 40), so L = 50, u = (0.6, 0.8), n = (−0.8, 0.6). For P = (20, 20): s = 12 + 16 = 28, t = −16 + 12 = −4, i.e. 28 m along and 4 m to the right. Check: √(28² + 4²) = √800 = |AP|. With W = 10, P is inside (|t| ≤ 5, 0 ≤ s ≤ 50). The point (10, 30) gives s = 30, t = +10: left of the line and outside.

interface Band { ax: number; ay: number; ux: number; uy: number;
                 nx: number; ny: number; length: number; half: number }

const MIN_LENGTH = 0.05;   // A and B closer than 5 cm: no usable direction
const END_TOL = 1e-4;      // 0.1 mm slack at the two ends (see the float32 section)

function makeBand(ax: number, ay: number, bx: number, by: number, width: number): Band | null {
  if (![ax, ay, bx, by, width].every(Number.isFinite) || width <= 0) return null;
  const dx = bx - ax, dy = by - ay;
  const length = Math.hypot(dx, dy);          // horizontal only: z never enters
  if (!Number.isFinite(length) || length < MIN_LENGTH) return null;
  const ux = dx / length, uy = dy / length;
  return { ax, ay, ux, uy, nx: -uy, ny: ux, length, half: width / 2 };
}

function insideBand(b: Band, px: number, py: number): boolean {
  const apx = px - b.ax, apy = py - b.ay;     // subtract first, keep numbers small
  const t = apx * b.nx + apy * b.ny;
  if (Math.abs(t) > b.half) return false;
  const s = apx * b.ux + apy * b.uy;
  return s >= -END_TOL && s <= b.length + END_TOL;
}

The band is built once; each point needs a translation and two dot products. Station uses (x, y) only, so a height difference between A and B can't stretch the horizontal axis. The same insideBand serves fresh extraction, re-filtering when the user narrows W, and hover. Re-filtering matched a fresh extraction without new loads. That assumes the wider extraction is complete and retained; widening needs more data. Sharing the predicate keeps boundary decisions consistent.

Pitfall: <= doesn't protect you from rounding. With A = (0, 0), B = (1, 6) and W = 2, a point built exactly 1 m off the axis can come out at 1.0000000000000004 and be rejected. I accepted that on the sides. The ends needed a deliberate tolerance, for a reason covered below.

Skip whole nodes

A large point cloud is stored as an octree of nodes, each with a bounding box, fetched on demand. To avoid downloading everything, I needed to reject whole nodes by looking only at their boxes.

Compute station and offset for the four corners of the box's footprint. Both are affine in position, so every point inside the box falls between the corner minimum and maximum. If the whole offset range is beyond W/2 on one side, or the station range ends before A or starts after B, nothing inside can be in the band. This is the separating axis test for two rectangles: the band's axes u and n, plus x and y via a cheap bounding-box check.

// Broad-phase roundoff margin for this metre-scale example, not a point tolerance.
const CULL_PAD = 1e-4;

function overlapsBandBounds(b: Band, minX: number, minY: number, maxX: number, maxY: number): boolean {
  const x0 = b.ax - b.ux * END_TOL, y0 = b.ay - b.uy * END_TOL;
  const x1 = b.ax + b.ux * (b.length + END_TOL);
  const y1 = b.ay + b.uy * (b.length + END_TOL);
  const hx = Math.abs(b.nx) * b.half + CULL_PAD;
  const hy = Math.abs(b.ny) * b.half + CULL_PAD;
  return maxX >= Math.min(x0, x1) - hx && minX <= Math.max(x0, x1) + hx
      && maxY >= Math.min(y0, y1) - hy && minY <= Math.max(y0, y1) + hy;
}

function boxTouchesBand(b: Band, minX: number, minY: number, maxX: number, maxY: number): boolean {
  if (!overlapsBandBounds(b, minX, minY, maxX, maxY)) return false;  // x and y axes
  let sMin = Infinity, sMax = -Infinity, tMin = Infinity, tMax = -Infinity;
  for (const [x, y] of [[minX, minY], [maxX, minY], [minX, maxY], [maxX, maxY]]) {
    const apx = x - b.ax, apy = y - b.ay;
    const s = apx * b.ux + apy * b.uy, t = apx * b.nx + apy * b.ny;
    sMin = Math.min(sMin, s); sMax = Math.max(sMax, s);
    tMin = Math.min(tMin, t); tMax = Math.max(tMax, t);
  }
  if (sMax < -END_TOL - CULL_PAD || sMin > b.length + END_TOL + CULL_PAD) return false;   // u axis
  if (tMax < -b.half - CULL_PAD || tMin > b.half + CULL_PAD) return false;                // n axis
  return true;  // possible overlap; individual points still get insideBand
}

The test may only err in one direction. Keeping a box that misses the band wastes a download. Rejecting one that touches it silently loses data. Randomized tests looked for rejected boxes containing in-band points; passing them is useful evidence, not a proof. The cheap bounds include END_TOL too. The extra culling margin favours false positives; node boxes must also enclose decoded coordinates, including decoding error.

Two traversal details came straight from the bug I was replacing. A known set, keyed by stable node ID and marked when queued, prevents repeated scans. Loads use only part of the viewer's shared concurrency budget, leaving room for rendering requests. In the loader I used, node.load() can silently decline when slots are full. I check whether loading actually started, and retry later if it did not. An empty ready queue is not completion while loads or hierarchy discovery remain pending.

Keep coordinates local

Projected map coordinates can be large. Use synthetic easting 400,000 and northing 3,900,000, both in metres, with no geographic location attached. JavaScript numbers are float64; the position buffers in this viewer use Float32. Those representations have very different spacing.

A normal Float32 has 24 bits of significand, including an implicit leading bit. Within the power-of-two interval containing a positive normal value v, consecutive floats are 2^(⌊log₂ v⌋ − 23) apart. 3,900,000 lies between 2²¹ (2,097,152) and 2²² (4,194,304), so the exponent is 21 and the spacing is 2²¹⁻²³ = 2⁻² = 0.25 m. Storing an absolute northing in this interval as Float32 snaps it to a quarter-metre grid, with a maximum round-to-nearest error of 0.125 m.

ValueExponentRepresentable spacing
northing 3,900,000210.25 m
easting 400,000180.03125 m
local value 8,000 (relative to a node corner)120.00049 m (about half a millimetre)
northing 3,900,000 in float64212⁻³¹ ≈ 0.5 nm

For a synthetic 0.1 m band, rounding northings to that grid can change membership near its edges; orientation matters. Subtracting an origin afterwards cannot recover discarded bits. I keep the origin precise and store small offsets from the start.

  • Extraction: the decoder stores each point as a Float32 offset from its node's box corner. I add the corner in float64, in the common coordinate frame. This preserves the local buffer's precision, not precision already lost during decoding.
  • 3D overlay: store band vertices relative to A. The renderer must combine the origin and camera transform in float64 before uploading a camera-relative transform; sending large translations separately to Float32 shaders can reintroduce the error.
  • Picking A and B: clicks resolve against the render copy, so the decoded position can land just past the endpoint it defines. The 0.1 mm end tolerance addresses that mismatch in this implementation; it is not a universal error bound for arbitrary node sizes.

Give each frame room

The scanner shares the main thread with input handling, layout, and rendering work. At 60 Hz, a frame interval is about 16.7 ms. A sufficiently large uninterrupted scan blocks interaction; point count alone does not tell me how long it will take.

So the extractor yields. It scans in chunks of 2,000 points, checks the clock after each chunk, and stops after about 6 ms, saving where it stopped for the next requestAnimationFrame. In an idealized example, 300 ms of CPU work takes roughly 50 slices and 0.83 s at 60 Hz, excluding loading and other overhead. That buys opportunities to render, not a frame-rate guarantee. Batch delivery and drawing also consume time; hidden tabs may pause these callbacks.

The scan loop below uses application-specific NodeQueue and Batch types. nextReady() returns only loaded, retained arrays; done means discovery and loading have finished and no ready nodes remain. Loading and error settlement live outside this sketch:

const BUDGET_MS = 6, CHUNK = 2_000;
let latestRun = 0;

function extract(band: Band, queue: NodeQueue, onBatch: (b: Batch) => void, signal: AbortSignal) {
  const run = ++latestRun;                       // stamped when the request is made
  const stale = () => signal.aborted || run !== latestRun;
  let node = queue.nextReady(), i = 0;
  const step = () => {
    if (stale()) return;
    const deadline = performance.now() + BUDGET_MS;
    if (!node) { node = queue.nextReady(); i = 0; }
    const batch = new Batch();
    while (node && performance.now() < deadline) {
      const end = Math.min(i + CHUNK, node.count);
      for (; i < end; i++) {
        const x = node.originX + node.localX[i];  // float64 + float32 offset
        const y = node.originY + node.localY[i];
        if (insideBand(band, x, y)) batch.push(node, i, x, y);
      }
      if (i === node.count) { node = queue.nextReady(); i = 0; }
    }
    if (stale()) return;
    onBatch(batch);
    if (!stale() && (node || !queue.done)) requestAnimationFrame(step);  // the callback may have cancelled us
  };
  requestAnimationFrame(step);
}

The scanner retains the actual point arrays across frames; holding a node object alone is insufficient if cache eviction clears its geometry. The queue prioritizes larger boxes so coarse coverage arrives before detail. That improves the preview, but a coarse profile cannot establish the final maximum elevation.

Reject stale results

Work spread over several frames can finish after its question has changed. Drag the width handle, and batches for the old width keep arriving and draw old heights over the preview.

I give each request a revision: capture it when the request is made, increment it whenever relevant state changes, and compare it where results land. If rendering is queued separately, that consumer must check too. The sketch assumes one active profile; separate profiles need separate counters.

Ignoring a result and cancelling the work are different jobs, so I use both:

  • Revision counter lets the consumer reject stale output without cooperation from the producer.
  • AbortSignal requests cancellation. The producer must check it, including after callbacks. Already-started shared loads may need to finish; aborting one profile must not cancel a load the renderer still needs.

Both bugs I hit here came up in review. The width drag debounced the next extraction but didn't stop the current one, which kept pushing batches. Debounce delays new work; it doesn't stop old work. Now the revision changes and cancellation is requested immediately, before the debounce; synchronous work stops at its next check. And a hover pick waiting for the camera to settle read the current revision when it finally ran, stamping an old cursor position as fresh. A revision only protects you if it is captured at creation.

Draw without distorting

The chart is a 2D canvas: station on x, elevation on y, flipped because pixels count downward. The catch is scale. For a synthetic 40 m section with 4 m of relief and a 720×300 px plot area inside an 800×400 canvas, the scales are 18 px per horizontal metre and 75 px per vertical metre. "Fit" mode exaggerates the vertical by 75 / 18 ≈ 4.17×.

So the chart offers a fixed vertical exaggeration V×N: one vertical metre takes N times the pixels of a horizontal one. It widens one axis around the view centre to hit that ratio without cropping data, and re-applies it on every view change. An early version applied it only once, letting scroll-wheel zoom drift away from the requested ratio.

Measurements use station and elevation, never pixels. I order endpoints by station and require a positive separation; equal stations have no finite grade. Take (10 m, 100 m) and (30 m, 102 m): Δd = 20 m, Δz = 2 m, slope = 2 / 20 = 10%, angle = atan2(2, 20) ≈ 5.71° once converted from radians. The grade is signed rise over horizontal run, with the same value at V×1 or V×10. This is grade along the profile axis; offsets across the band are ignored. Vegetation and structures can appear here too, so interpreting it as ground slope requires ground returns.

Drawing is budgeted too: a capped batch of new points per frame while data streams in, a capped every-k-th-point preview during zoom and pan, a deferred full redraw after the user stops, and points grouped by colour so fillStyle changes once per group.

Check with a second reader

"The chart looks right" is not evidence. I checked the same COPC file with a separate reader, decoded in float64, using an independently written band test. Both tests included the nominal edges; only my extractor extended the ends. Match source records rather than rounded coordinates: distinct returns can share a position. The comparison found:

  • Every point the independent reader found was also in my result.
  • The extras were A and B themselves, admitted by the end tolerance after small coordinate differences moved them across the nominal boundary.
  • Coordinate differences were at micrometre scale in that comparison, not evidence of micrometre survey accuracy.
  • Changing the viewer's point budget and orbiting the camera gave the same count, as expected for traversal independent of screen visibility.
  • Cancellation tests produced no subsequent callbacks. A temporary point cap stopped at the configured limit and reported partial.

The serious bugs were on unhappy paths: a stalled load that fell out of the in-flight count (so the extractor exceeded its own load cap), callbacks after cancellation, and a completion promise that could hang if a caller's callback threw. Now stalled loads stay counted, cancellation is rechecked after callbacks, and each terminal path settles as complete, partial, cancelled, or error.

Takeaways

  • Spike on real data before planning. A comparison turned "wrap the built-in tool" into "write an extractor"; other datasets confirmed the problem in that integration.
  • One invariant, one place. One insideBand for extraction, re-filtering, and hover. Vertical exaggeration applied wherever the view is computed, not in one event handler.
  • Subtract before you compute. Large coordinates go through float64 and a nearby origin; Float32 only ever holds small offsets.
  • Long work yields. A small per-frame budget, saved progress, and a held reference to the data being scanned.
  • Every async result answers an old question. Stamp requests at creation, invalidate old work immediately, and check again after every callback.
  • Cross-check with a second implementation, and write down what you haven't measured yet.
